# Desktop Dles MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Tauri desktop app with a Settings page to store game URLs and a Routine page showing the list beside the live game page.

**Architecture:** One native window created in Rust. A full-size "ui" webview renders the React app. Each game is a child webview (`Window::add_child`, `unstable` feature) placed over the panel area, created on first open, kept alive and hidden when another game is shown. Pure TypeScript modules hold the routine logic and the SQLite access, so both are tested without Tauri.

**Tech Stack:** Tauri 2.12 (`unstable`), Rust stable, Vite, React 19, TypeScript, TanStack Router (SPA, hash history), `@tauri-apps/plugin-sql` (SQLite), `@tauri-apps/plugin-opener`, Vitest, Biome, pnpm.

**Spec:** `docs/superpowers/specs/2026-11-03-mvp-design.md`

## Global Constraints

- UI copy is English. Every user-facing string lives in `src/strings.ts`.
- The app injects no script into game sites: no `initialization_script`, no `eval` on a game webview.
- Game webviews match no capability. The only capability targets `webviews: ["ui"]`, never `windows`.
- A game URL must start with `https://`.
- Shuffle happens once per app launch. "Opened" lives in memory for the session only.
- One shared persistent session store for all games (Tauri default). No `data_directory`, no per-game store.
- New-window requests from a game (`target="_blank"`, `window.open`) open in the system browser.
- macOS is the target platform for verification. No signing, no bundling, no Linux or Windows checks.
- Bundle identifier: `io.github.ludovicnoirault.desktopdles`. Product name: `Desktop Dles`.
- Commit messages: conventional commits, no co-author or tool attribution.

## Review Focus

1. **Capability scope.** The Tauri template's default capability uses `windows: ["main"]`, which also links every child webview of that window, games included. A game page calling `invoke` must be refused. Tauri also allows app commands from every webview unless the app declares an app manifest. Pinned in Task 1 (capability file), Task 4 (app manifest in `build.rs`) and Task 6 (devtools check).
2. **A game that never loads.** Offline, wrong URL or slow site: "Next game" and "Reload" must still work, since the UI never waits on page load. Pinned in Task 6 with an unreachable URL.
3. **Settings edits while a routine is open.** Deleting the current game, deleting all games, or adding one must keep the routine consistent with no index out of range. Pinned in Task 2 (`routineReducer` sync tests).
4. **Hostile or sloppy URL input.** `http://`, `javascript:`, surrounding spaces, `https://` alone. Pinned in Task 2 (`isValidGameUrl` tests).
5. **The game panel covering app UI.** After window resize, and on the Settings page, the native game view must follow the panel or be hidden. Pinned in Task 5 (bounds sync and hide on leave) and Task 6 (manual check).

- [ ] **Step 3: Implement `src/routine/routine.ts`**

`buildRoutine` uses Fisher-Yates driven by `rng`. `sync` keeps the current game selected if it still exists (by id), else clamps `current` to the new length minus one (0 when empty). `sync` drops deleted ids from `opened`, and when the current game changes, the new current id joins `opened`. With shuffle off, `sync` rebuilds from positions. With shuffle on, it keeps the existing order, drops deleted ids and appends new ones in position order. Settings edits apply to the open routine through `sync`.

- [ ] **Step 2: Implement `games.rs`**

`show_game` gets window `main`. If webview `game_label(id)` exists, it calls `set_bounds` and `show`. Otherwise it calls `add_child` with `WebviewBuilder::new(label, WebviewUrl::External(url))`. The builder gets an `on_new_window` handler that opens the URL with `tauri-plugin-opener` and returns `NewWindowResponse::Deny`. Then `show_game` hides every other webview whose label starts with `game-`. `set_game_bounds` applies `Rect { position: LogicalPosition, size: LogicalSize }` to every `game-*` webview. `reload_game` calls `navigate(url)`. `close_game` calls `close`. URLs are parsed with `Url::parse`, and an error becomes `Err(String)`. No `initialization_script`. The commands are `async` because creating a webview from a synchronous command deadlocks on Windows, the next target.

- [ ] **Step 3: Register and allow**

Register the opener plugin and the five commands. Tauri allows app commands from every webview unless the app declares an app manifest, so `build.rs` calls `tauri_build::try_build(tauri_build::Attributes::new().app_manifest(tauri_build::AppManifest::new().commands(&[...])))` with the five command names. Add their generated permissions (`allow-show-game`, `allow-set-game-bounds`, `allow-hide-games`, `allow-reload-game`, `allow-close-game`; check the exact identifiers in the generated schema) to `ui.json`, which stays the only capability. The opener is called from Rust only, so `ui.json` gets no `opener` permission.
